# 2D RPG 简化改造计划

状态：第一至第三阶段已有运行时代码迁移与新增实现；具体修改及验证情况见 ChangeLog.md、TemporaryFXBaseline.md。代码存在不等于 Unity 实测通过；第四、第五阶段仍按下述目标推进。更新于 2026-11-08。

## 目标与约束

以复用 mmo-demo 的架构、事件、UI、对话和 TCP 代码为主，逐步整理 rpg。先保证容易理解、功能可运行，不追求通用引擎或大量新技术。

保留 Unity 2021.3、现有 2D 物理、动画、战斗状态机、技能、背包与存档。保护用户尚未提交的场景、骷髅预制体和墙跳代码。每次改造前说明旧流程、新流程、必要概念和验收方式。

保留并核验现有玩家与敌人 FSM：按各角色实际能力覆盖移动、跳跃、攻击、受击和死亡，不要求所有敌人都具备跳跃等相同状态。保留多形态技能、技能树、背包、装备与合成系统；物品继续使用 ScriptableObject 配置，对话使用 DialogueAsset 配置。以上是现有功能的保留与回归范围，不作为重新开发整套系统的要求。

分层与 IOC 先用于背包的数据、规则和 UI 分离，再按实际依赖整理技能、战斗和 UI 的必要接口。通过委托与事件通知变化，不要求将所有直接调用改成事件，也不将局部接入描述成全项目已经完成解耦。

## 第一阶段：复用模块与事件，整理背包

从 mmo-demo 迁移并精简 Architecture、IOCContainer、层接口和事件注册发送注销代码。采用明确的启动顺序，补充必要的退出清理；不直接复制其登录启动和 Hotfix 反射入口。

先接入背包：分开保存数据、添加移除装备等规则和 UI 刷新。保留物品 ID、合成规则、存档格式及场景绑定，减少一次性迁移范围。用现有事件机制通知 UI；逐步检查事件载荷和取消订阅，不为统一事件而改写所有方法调用。

验收：拾取、堆叠、装备、合成和存取档保持正确，界面反复开关无重复回调。

## 第二阶段：复用 UI、对话和交互

按需复用 BasePanel、UISystem 通用部分，不照搬登录角色数据和场景名。保留 rpg 现有菜单与 HUD。

迁移 DialogueAsset、DialogueRunner；适配 InteractionManager、InteractionOptionData 和 NpcInteractable，将 3D Collider 回调改为 2D，替换玩家识别和界面引用。

参考 GameplayControlLock，整理对话、菜单和聊天期间的输入屏蔽。多个界面同时锁定时，不允许关闭其中一个就恢复全部输入。保留当前技能实现，仅整理必要输入入口。

保留现有对话遮罩与暂停策略，核验实际输入入口及关闭当帧是否会误触发操作；当前已有按持有者申请、释放的输入锁时直接复用，避免再建一套。没有聊天功能时不新增聊天 UI 或网络聊天，只保留后续接入方式。

验收：NPC 对话、分支选择、离开和关闭正常；对话期间不会触发移动、攻击或技能。任务系统不在本阶段范围内。

## 第三阶段：小型对象池

mmo-demo 当前没有发现现成对象池，需要新增一个用途明确的小型实现。只先接伤害数字、命中特效和残影，不扩展为全功能池框架。

提供取出、归还、容量限制和场景清理。重置透明度、缩放、计时器、协程与延迟回调；同步移除旧的延迟 Destroy。

验收：对象反复复用状态正确，战斗效果保持正常，用 Profiler 比较创建销毁和 GC 分配。

分别检查伤害飘字、普通/暴击命中特效和残影的预制体绑定及实际播放。缺少可用预制体或尚未接入的效果单独列为待办，不能只凭脚本存在宣称完成。性能比较使用相同战斗操作，区分首次创建与缓存复用；记录 Instantiate、Destroy 和 GC Alloc 的实际变化。没有改造前采样时，仅报告当前复用表现，不填写未经测量的提升比例；完整战斗不要求零分配。

## 第四阶段：复用网络代码，采用玩家主机房间模式

玩家 A 创建房间并兼任主机，玩家 B 加入房间。A 负责权威状态计算和战斗结果裁决，B 发送操作请求并接收主机同步结果。

复用 NetPacket、NetSystem 的 TCP 收发、接收队列和主线程派发；检查并适配主机监听、客户端连接、断线清理和失败处理。

通信基于 C# TcpClient、NetworkStream 封装；A 的监听与接受连接另行实现，可使用 TcpListener。复用长度前缀协议：int32 包体长度（包含协议号，不包含长度字段本身）＋int16 协议号＋UTF-8 JSON，明确两端字节序与最大包长。循环读取完整长度头和包体，覆盖拆包、连续多包及中途断线，不能假定一次 Read 就是一条消息。

后台接收线程只读取、组包并将消息放入加锁队列；主线程 Update 取出、解析和分发，再更新 Unity 对象。退出时关闭连接、结束收包线程并清理待处理消息，避免旧会话消息进入新房间。

实施顺序：创建与加入房间 → 双人移动同步 → 主机控制怪物 → 攻击请求与伤害同步 → 死亡、掉落和拾取同步。

1. 创建与加入房间：A 创建房间，B 连接加入，完成玩家身份分配、进入同场景和实体初始化。
2. 双人移动同步：复用 LocalPlayerStateSender、RemotePlayerManager、RemotePlayerView 的相关结构，适配 2D 位置、左右朝向和动画状态。B 发送移动输入，由 A 计算并同步位置；远端角色不执行本地输入逻辑，显示使用简单插值。
3. 主机控制怪物：由 A 执行怪物 AI、移动和攻击，向 B 同步怪物状态。
4. 攻击请求与伤害同步：B 发送攻击或技能请求，A 校验冷却、距离和命中，计算伤害并同步生命值和结果；按实体和玩家区分技能、目标及归属。
5. 死亡、掉落和拾取同步：由 A 确认死亡、生成掉落并裁决拾取归属，同步结果，防止重复领取。战斗一致性规则需要补写，不能直接从位置同步得到。

约定 A 退出或主机连接中断即关闭房间，B 结束当前联机会话并清理网络实体；首版不做主机迁移。

同步频率与权威归属：mmo-demo 原实现默认每 0.1 秒由客户端上报位置、朝向和动画参数，远端插值显示；这属于复用参考，不能直接当成 rpg 已完成的行为。rpg 保持上述主机方案，计划默认每 100ms 由 A 向 B 同步角色权威状态；B 的移动输入发送另行处理，不能将最终位置上报与主机计算输入混为同一实现。最终项目描述应按实际实现写明发送方向、消息内容和实测频率。

暂不做本地预测回滚、复杂房间匹配或完整断线恢复。好友和私聊可复用 mmo-demo，但先作为选做内容。

验收：A 可创建房间，B 可加入并互相看见移动；怪物、伤害、生命值、死亡、掉落和拾取结果以 A 为准且两端一致；A 退出后房间关闭，B 正确结束会话；B 单独断线后，A 正确清理其角色与资源。

移动同步先单独完成同机双客户端验收：可用一个 Unity 编辑器实例加一个构建程序，或两个构建程序；A 创建、B 加入同一房间，两端分别操作并互相看见移动、朝向和动画更新。记录构建版本、运行组合、连接地址、同步间隔及结果，并保留截图、录像或日志。同机通过不等于局域网或公网通过；没有实际运行记录前，不写“已通过同机双客户端测试”。之后再单独验收协作战斗。

## 项目描述与完成证据

项目描述需区分已有代码、Unity 实测和后续计划。当前 rpg 已能找到分层/IOC、对话与交互、输入锁及临时特效池实现，但本计划不据此补记尚未完成的操作验收。当前 rpg 脚本目录未发现 TcpClient/NetworkStream 联机实现；mmo-demo 中的网络代码不能计作已经接入 rpg。

对外描述中的“每 100ms 上报角色状态”须与最终主机同步方向一致；“同机双客户端测试验证双方移动同步”须在实际验收后使用。若描述的是 mmo-demo 的已有实验，应独立注明项目及测试范围。复用、修改和自行新增的部分按实际贡献说明，不将复用代码统称为从零独立设计。

## 第五阶段：资源更新独立接入

保留资源更新目标，但放在基本功能稳定后进行。mmo-demo 当前 GameResSystem 是 Resources 加载缓存，没有发现 Addressables 更新链路；此部分需要新接入，不能标为代码直接复用。

先集中少量 UI、特效资源加载入口，再接兼容当前 Unity 的 Addressables。演示本地启动页、检查更新、下载进度、失败重试及新资源生效。保存更新构建所需文件并验证实际客户端，不承诺 C# 代码热更新。

## 交付顺序

1. 核对并保存可运行基线。
2. 迁移最小架构与事件，用背包完成一次接入。
3. 复用面板管理、对话与交互，整理输入锁。
4. 新增小型特效对象池。
5. 复用 TCP 和角色同步，建立 A 创建、B 加入的主机房间基础。
6. 按创建与加入房间 → 双人移动同步 → 主机控制怪物 → 攻击请求与伤害同步 → 死亡、掉落和拾取同步的顺序完成联机；A 退出即关闭房间。
7. 独立接入资源更新。

每一步均需编译、验证相关功能、解释调用流程，再推进下一步。不以添加接口数量作为完成标准。
